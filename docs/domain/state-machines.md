# CrownSourceGlobal — State Machines

Authoritative states and legal transitions for the entities whose lifecycle matters to correctness. See `/docs/domain/entities.md` for the fields these states live on.

| Entity | States (→ = transition) | Terminal | Triggered by | Idempotency note |
|---|---|---|---|---|
| **Quotation** *(INSTANT origin M5; CUSTOM_SOURCING origin + SUPERSEDED added M6)* | ISSUED → ACCEPTED \| EXPIRED \| SUPERSEDED | ACCEPTED, EXPIRED | System (issue — always already ISSUED, no persisted DRAFT row), Customer (accept, via `ordersService.createOrderFromQuotation`), Staff (supersede — CUSTOM_SOURCING only, via reissuing a quote through `modules/sourcing/service.ts`'s `prepareAndIssueQuote`) | `Order.originQuotationId` unique constraint — at most one Order per Quotation, ever, even under a race. EXPIRED is derived at read time from `expiresAt`, not a background sweep; acceptance independently re-checks expiry so correctness never depends on a scheduler running. ISSUED → SUPERSEDED happens atomically with the replacement quote's creation (same transaction) — never edited in place. `WITHDRAWN` remains unused/reserved. |
| **CustomSourcingRequest** *(implemented M6)* | SUBMITTED → UNDER_REVIEW → SOURCING ⇄ AWAITING_CUSTOMER → QUOTED → ACCEPTED; ⇢ UNABLE_TO_SOURCE; ⇢ CANCELLED | ACCEPTED, UNABLE_TO_SOURCE, CANCELLED | Customer (submit; cancel, only from SUBMITTED/UNDER_REVIEW/SOURCING/AWAITING_CUSTOMER); Staff (review/assign/source/request-clarification/resume/quote/mark-unable); System (ACCEPTED — set atomically with Order creation inside `ordersService.createOrderFromQuotation`'s transaction, the moment the request's Quotation is accepted, not when payment later confirms) | Every transition is a guarded `updateMany` with an explicit `fromStatuses` WHERE clause (same pattern as Fulfilment). QUOTED → QUOTED is legal (reissue/supersede) but SUBMITTED → SOURCING directly is not (must pass through UNDER_REVIEW). Customer can never set UNDER_REVIEW/SOURCING/QUOTED/UNABLE_TO_SOURCE/ACCEPTED directly — no customer-facing service function reaches any of them. |
| **Vendor Verification** | PENDING → UNDER_REVIEW → APPROVED \| REJECTED → (resubmit) PENDING | APPROVED, REJECTED (soft) | Vendor (submit), Admin (approve/reject) | — |
| **Vendor Listing** | DRAFT → PENDING_REVIEW → APPROVED → ACTIVE ⇄ INACTIVE; APPROVED → CHANGES_REQUESTED → PENDING_REVIEW; → REJECTED → (edit) PENDING_REVIEW; → ARCHIVED | ARCHIVED | Vendor (create/edit/toggle), Admin (approve/reject/request changes) | — |
| **Quotation** | DRAFT (internal, custom only) → ISSUED → ACCEPTED \| EXPIRED \| WITHDRAWN \| SUPERSEDED | ACCEPTED, EXPIRED, WITHDRAWN, SUPERSEDED | System (issue/expire), Customer (accept), Admin (withdraw/supersede) | Unique constraint: one Order per Quotation — ACCEPTED cannot fire twice |
| **Custom Sourcing Request** | SUBMITTED → UNDER_REVIEW → SOURCING → QUOTED → (resolved via linked Quotation) \| CLOSED_NO_QUOTE \| CANCELLED | CLOSED_NO_QUOTE, CANCELLED, or implicitly resolved once the linked Quotation is ACCEPTED | Customer (submit/cancel), Admin (review/source/quote/close) | — |
| **Order** (fulfilment track) | PENDING_PAYMENT → CONFIRMED → FULFILLING → COMPLETED \| CANCELLED (only from PENDING_PAYMENT or pre-fulfilment) | COMPLETED, CANCELLED | System (payment webhook → CONFIRMED; all Fulfilments COMPLETED → COMPLETED) | `Order.paymentStatus` is tracked on a **separate** field (UNPAID/PAID/PARTIALLY_REFUNDED/REFUNDED) to avoid a combinatorial status explosion — a COMPLETED order can still carry a REFUNDED paymentStatus |
| **Payment** *(provider-neutral; Moolre added M10A, Paystack primary as of M10A.2)* | INITIATED → PENDING → SUCCEEDED \| FAILED \| CANCELLED | SUCCEEDED, FAILED, CANCELLED | System (initiate), Provider webhook (trigger only) + independent server-to-server status verification (authoritative confirm/fail — Paystack's Verify Transaction, or Moolre's status endpoint) | `reference` (CrownSourceGlobal's own, also sent as Paystack's `reference`/Moolre's `externalref`) is the idempotency key across retries — never regenerated for the same attempt. `providerReference` unique constraint (the provider's own transaction id — see ADR 0007 for why this is now separate from `providerEventId`). A DB-only partial unique index (`payment_one_active_per_order`, not expressible in schema.prisma) enforces at most one INITIATED/PENDING Payment per Order at a time. `applyVerifyOutcome`'s SUCCEEDED transition is a guarded `updateMany` — N duplicate webhooks/polls/reconciliation calls can only ever produce one winner. CANCELLED is reserved for the abandoned-payment sweep (Workflow F); a Payment that succeeds after its Order was already swept to CANCELLED is never silently reopened — it's flagged via `exceptionReason` for manual admin resolution instead. |
| **Refund** *(implemented M9 — real model; executor routing generalized M10A.2 for real async providers)* | PENDING_APPROVAL → APPROVED → PROCESSING → COMPLETED \| FAILED; FAILED → (retry) PROCESSING | COMPLETED; FAILED is retryable, not terminal | Admin (`approveResolution()` creates it already APPROVED — amount/approval happen together, and links the Order's successful `Payment` as of M10A.2), System (`processRefund()` — executor selected by the linked Payment's own provider, moves APPROVED/FAILED → PROCESSING, then either resolves immediately (mock: COMPLETED/FAILED) or stays PROCESSING pending real-provider reconciliation (Paystack, asynchronous — `reconcilePaystackRefund`, admin-triggered or `refund.*` webhook-triggered, both independently re-verifying via `GET /refund/:reference`, never trusting a webhook body's embedded status)) | `claimRefundForProcessing()` is a guarded `updateMany` (`status: {in: ["APPROVED","FAILED"]}`) — a `COMPLETED` refund can never be re-claimed, so a duplicate "process refund" click cannot execute twice. Never a new record per retry — the same `Refund` row is retried in place, since `PROCESSING`/`FAILED` are both legitimately re-claimable states. `MoolreRefundExecutor` always fails closed (no documented API — ADR 0006/0007); it can never move a Refund to COMPLETED. |
| **Fulfilment** | PENDING → PREPARING → READY → DISPATCHED → DELIVERED → COMPLETED; ⇄ EXCEPTION; → CANCELLED | COMPLETED, CANCELLED | Vendor (start preparing, mark ready); READY → DISPATCHED is **origin-dependent** — domestic: Admin only, on collection confirmation; international: **Vendor**, by recording outbound shipment details (per M4, refining the earlier "vendor may dispatch" note — a vendor may never single-handedly move a *domestic* Fulfilment past READY). DELIVERED is System/Admin only, set when the linked Shipment reaches DELIVERED. EXCEPTION is Vendor (report issue) or Admin (delivery failure); resolution (Admin) resumes to PREPARING. ACCEPTED is modeled but unused in M4 (Vendor goes PENDING→PREPARING directly). | Creation is idempotent per Order-confirmation event, not per vendor — since multiple Fulfilments per vendor per Order are legal, vendor-scoped uniqueness cannot be the dedup key. Uses the `Order.fulfilmentsCreatedAt` flag. |
| **Shipment** *(implemented M4)* | CREATED → COLLECTED → IN_TRANSIT → OUT_FOR_DELIVERY → DELIVERED; ⇄ EXCEPTION; OUT_FOR_DELIVERY/IN_TRANSIT → DELIVERY_FAILED → (resume) OUT_FOR_DELIVERY | DELIVERED | Admin/operations only for every status transition — CREATED→COLLECTED is the one moment that means either "domestic pickup confirmed" or "international receipt confirmed" (both land on the same status; disambiguated by `Fulfilment.origin` for display). A customer's `customerConfirmedReceiptAt` is a side signal recorded independently and never itself sets `status = DELIVERED`. | One active Shipment per Fulfilment in the V1 UI (schema allows more later — see entities.md). Confirming collection/receipt requires `status = CREATED`, preventing a double-confirm. |
| **FulfilmentIssue** *(added M4)* | OPEN → RESOLVED | RESOLVED | Vendor (report — only while the parent Fulfilment is PENDING/PREPARING/READY), Admin (resolve, which also resumes the parent Fulfilment to PREPARING) | — |
| **VendorEarning** *(implemented M11 — supersedes the never-populated `FulfilmentItem.payoutEligibility`, removed this milestone; lifecycle split M11.1)* | PENDING → WAITING_PERIOD → ELIGIBLE → INCLUDED_IN_SETTLEMENT → PAID; ⇄ ON_HOLD (from PENDING/WAITING_PERIOD/ELIGIBLE); ⇢ CANCELLED (from PENDING/WAITING_PERIOD/ON_HOLD/ELIGIBLE) | PAID, CANCELLED | System (created PENDING at Fulfilment-creation time — Order confirmation or a resolution-case replacement); System (`modules/fulfilment/repository.ts`'s `progressShipment` — PENDING → WAITING_PERIOD, event-driven, the instant the parent Fulfilment reaches DELIVERED, `deliveredAt` stamped in the same transaction); System (`sweepEligibleEarnings` — WAITING_PERIOD → ELIGIBLE once `VENDOR_PAYOUT_HOLD_HOURS` has elapsed since `deliveredAt`; never touches any other state); `resolutionsRepository.approveResolutionTransactional` (PENDING/WAITING_PERIOD/ELIGIBLE → ON_HOLD for a partial/replacement decision, same transaction as `payoutHold`; OR straight → CANCELLED for a full Vendor-attributable refund/return covering the entire FulfilmentItem quantity — see `policy.ts`'s `isFullVendorClosure` — never parked ON_HOLD first); `resolutionsService.resolveCase` (ON_HOLD → PENDING/WAITING_PERIOD/ELIGIBLE, release — restores wherever the earning would legitimately be had the hold never happened, based on `deliveredAt`, never a blind reset to PENDING); `vendorFinanceService.createSettlement`/`recordPayout` (ELIGIBLE → INCLUDED_IN_SETTLEMENT → PAID); cancellation of the parent Fulfilment (→ CANCELLED) | `fulfilmentItemId` is `@unique` — exactly one Earning per FulfilmentItem, ever. Settlement inclusion is a guarded `updateMany` (`status: "ELIGIBLE"`) — two concurrent settlement-creation attempts can only ever have one claim a given earning; the `VendorSettlementItem.vendorEarningId` unique constraint is the DB-level backstop. `originalPayableAmount` is never rewritten — corrections are always additive `VendorFinancialAdjustment` rows (ADR 0005's mechanism, now implemented). |
| **VendorSettlement** *(implemented M11, manual-payout mode; automated Paystack payout added M12 — see ADR 0010)* | DRAFT → APPROVED → PAID (manual path, unchanged since M11); DRAFT → APPROVED → PROCESSING → PAID/FAILED (automated path, M12), FAILED → PROCESSING (retry, generates a fresh `payoutProviderReference`); DRAFT/APPROVED/FAILED → CANCELLED (releases its earnings back to ELIGIBLE) | PAID, CANCELLED | Admin (create — DRAFT; approve — snapshots the Vendor's payout destination; cancel); Admin (`recordPayout` — APPROVED → PAID, manual, only after money has already been sent externally); Admin (`initiatePayout`/"Send Payout" or "Retry Payout" — APPROVED/FAILED → PROCESSING, then a real Paystack Transfer; System/Admin (`checkPayoutStatus`/webhook — PROCESSING → PAID/FAILED, or stays PROCESSING if still uncertain) | `approveSettlementTransactional`/`recordPayoutTransactional`/`claimSettlementForPayout`/`markPayoutPaidTransactional`/`markPayoutFailedTransactional` are all guarded `updateMany`s keyed on the settlement's own current status — a double-click, a race between two Admins, or a duplicate webhook can only ever produce one winner. The manual and automated paths cannot conflict by construction: manual recording requires `status = "APPROVED"`; automated claiming requires `status IN ("APPROVED","FAILED")` and immediately flips to `"PROCESSING"` — whichever path wins, the other's WHERE clause no longer matches. A network/timeout error talking to Paystack is mapped to neither PAID nor FAILED — it leaves the settlement PROCESSING (genuinely uncertain), resolved later only via independent re-verification, never a blind retry. PAID is never mutated in place afterward; a wrongly-recorded payout (either path) is corrected via `reverseSettlementTransactional`, which sets `reversedAt`/`reversalReason` (additive markers, original amount/reference stay visible) and creates a negative `SETTLEMENT_REVERSAL` adjustment per included earning, netted into a future Settlement — never a reverse transfer. |
| **EmailDeliveryJob** *(implemented M7)* | PENDING → SENDING → SENT \| FAILED; FAILED → (retry) SENDING while `attempts < maxAttempts`, else FAILED is terminal | SENT; FAILED once `attempts = maxAttempts` | System (`notify()` creates PENDING; the drain worker claims/sends/marks) | Claim is an atomic guarded `updateMany` (`where: {id, status: eligible.status}`) — the cross-process mutual-exclusion mechanism when multiple drain calls run concurrently. Bounded backoff on failure: `[1m, 5m, 30m, 2h, 12h]` indexed by attempt count, capped at the last value. An exhausted job (`attempts = maxAttempts`, `status = FAILED`) is never reclaimed — the claim query's `attempts < maxAttempts` filter excludes it permanently; no separate terminal enum value needed. |
| **ResolutionCase** *(implemented M9)* | OPEN → UNDER_REVIEW → (AWAITING_CUSTOMER \| AWAITING_VENDOR, either → UNDER_REVIEW) → RESOLUTION_APPROVED → RESOLUTION_IN_PROGRESS → RESOLVED → CLOSED; ⇢ REJECTED (from OPEN/UNDER_REVIEW/either awaiting-state) | CLOSED (REJECTED is a soft/reviewable terminal, matching Vendor Verification's pattern) | Customer (submit — always lands OPEN), Staff (every other transition — a Customer/Vendor can never move a case past OPEN) | Every transition is a guarded `updateMany` with an explicit `fromStatuses` WHERE clause (same pattern as Fulfilment/CustomSourcingRequest). `RESOLUTION_IN_PROGRESS` is modeled but not currently a required stop — same "modeled for future use, not forced into the current flow" pattern as `Fulfilment.ACCEPTED` in M4. |
| **Return** *(implemented M9)* | APPROVED → IN_TRANSIT → RECEIVED → INSPECTED → COMPLETED | COMPLETED | Staff only, every transition (Customer never touches Return status directly — reverse logistics is CrownSource-managed, not self-service) | `inspectionOutcome = RESELLABLE` at the INSPECTED step is what triggers a restock, guarded by `restockedAt` so it can only ever happen once per Return, regardless of how many times the case is later revisited. |

**FulfilmentItem payout hold** *(implemented M9, mechanism built M4/ADR 0005)* is a boolean side-flag, not a state machine: `payoutHold`/`payoutHoldReason` are set by `approveResolution()` when `responsibility = VENDOR` and the decision is refund-bearing or a replacement — M9's own code is unchanged by M11. The same transaction now additionally moves the affected `VendorEarning`(s) to `ON_HOLD` and, when a refund amount was approved, creates a negative `VendorFinancialAdjustment` (M11 — see the VendorEarning row above and ADR 0009).

**VendorFinancialAdjustment** *(implemented M11 — this is ADR 0005's `PayoutAdjustment`, built)* is not a state machine — it's an immutable, additive-only row (signed `amount`, never edited or deleted) with one mutable field: `appliedToSettlementId`, set exactly once when swept into a Settlement at creation time (`createSettlement`), read as `null` to mean "outstanding, will net into the vendor's next Settlement." Created by `resolutionsRepository.approveResolutionTransactional` (category `RESOLUTION_REFUND`), an admin manual correction (`MANUAL_CORRECTION`), or `reverseSettlementTransactional` (`SETTLEMENT_REVERSAL`) — regardless of whether the linked `VendorEarning` has already reached `PAID` (the "post-settlement refund" case).

**Notification read state** *(implemented M7)* is a simple two-state flag, not a full machine: unread (`readAt = null`) on creation → read (`readAt` set) via `markRead`/`markAllRead`, both scoped to the owning `recipientUserId` and idempotent (marking an already-read notification read again is a no-op, not an error).

## Notes

- **Order/package display status is derived, not a state machine** *(added M11.1)* — `modules/orders/display-status.ts`'s `computeOrderDisplayStatus` reads the real states above (Fulfilment, Shipment, ResolutionCase, Refund, Return, Replacement) and layers a small human-facing label on top (`ISSUE_UNDER_REVIEW`, `RETURN_IN_PROGRESS`, `REFUND_PROCESSING`, `REFUNDED`, `PARTIALLY_REFUNDED`, `REPLACEMENT_IN_PROGRESS`, or the plain logistics stage). It has no persisted field and no transitions of its own — it is recomputed at read time from whichever of the above states currently hold, and never overwrites any of them (a delivered Shipment stays recorded as DELIVERED forever, even while the Order displays REFUNDED).
- **FulfilmentItem has no independent full state machine** in V1 — its parent Fulfilment carries the primary status, avoiding overbuilt granularity where it isn't needed yet.
- The **payout eligibility trigger** is resolved as of M11: `Fulfilment.status = DELIVERED`, not `COMPLETED` — nothing in the codebase has ever transitioned a Fulfilment to `COMPLETED` (a pre-existing M4/M5 gap, out of scope for M11 to fix), so `DELIVERED` was the only trigger that could actually be observed. See ADR 0009.
- **Refund/payout interaction** across these state machines is detailed in `/docs/workflows/workflows.md` (Workflow K) and ADR 0005 for the pre-M9 mechanism design, and Workflows S–V (M9) for the actual post-purchase-resolution flows now built on top of it.
- **ResolutionCaseItem has no independent state machine** — its `approvedResolution` field is set once, atomically, by `approveResolution()`; there's no multi-step lifecycle at the line level beyond "undecided → decided."
