# CrownSourceGlobal — State Machines

Authoritative states and legal transitions for the entities whose lifecycle matters to correctness. See `/docs/domain/entities.md` for the fields these states live on.

| Entity | States (→ = transition) | Terminal | Triggered by | Idempotency note |
|---|---|---|---|---|
| **Quotation** *(INSTANT origin M5; CUSTOM_SOURCING origin + SUPERSEDED added M6)* | ISSUED → ACCEPTED \| EXPIRED \| SUPERSEDED | ACCEPTED, EXPIRED | System (issue — always already ISSUED, no persisted DRAFT row), Customer (accept, via `ordersService.createOrderFromQuotation`), Staff (supersede — CUSTOM_SOURCING only, via reissuing a quote through `modules/sourcing/service.ts`'s `prepareAndIssueQuote`) | `Order.originQuotationId` unique constraint — at most one Order per Quotation, ever, even under a race. EXPIRED is derived at read time from `expiresAt`, not a background sweep; acceptance independently re-checks expiry so correctness never depends on a scheduler running. ISSUED → SUPERSEDED happens atomically with the replacement quote's creation (same transaction) — never edited in place. `WITHDRAWN` remains unused/reserved. |
| **CustomSourcingRequest** *(implemented M6)* | SUBMITTED → UNDER_REVIEW → SOURCING ⇄ AWAITING_CUSTOMER → QUOTED → ACCEPTED; ⇢ UNABLE_TO_SOURCE; ⇢ CANCELLED | ACCEPTED, UNABLE_TO_SOURCE, CANCELLED | Customer (submit; cancel, only from SUBMITTED/UNDER_REVIEW/SOURCING/AWAITING_CUSTOMER); Staff (review/assign/source/request-clarification/resume/quote/mark-unable); System (ACCEPTED — set atomically with Order creation inside `ordersService.createOrderFromQuotation`'s transaction, the moment the request's Quotation is accepted, not when payment later confirms) | Every transition is a guarded `updateMany` with an explicit `fromStatuses` WHERE clause (same pattern as Fulfilment). QUOTED → QUOTED is legal (reissue/supersede) but SUBMITTED → SOURCING directly is not (must pass through UNDER_REVIEW). Customer can never set UNDER_REVIEW/SOURCING/QUOTED/UNABLE_TO_SOURCE/ACCEPTED directly — no customer-facing service function reaches any of them. |
| **Vendor Verification** | PENDING → UNDER_REVIEW → APPROVED \| REJECTED → (resubmit) PENDING | APPROVED, REJECTED (soft) | Vendor (submit), Admin (approve/reject) | — |
| **Vendor Listing** | DRAFT → PENDING_REVIEW → APPROVED → ACTIVE ⇄ INACTIVE; APPROVED → CHANGES_REQUESTED → PENDING_REVIEW; → REJECTED → (edit) PENDING_REVIEW; → ARCHIVED | ARCHIVED | Vendor (create/edit/toggle), Admin (approve/reject/request changes) | — |
| **Quotation** | DRAFT (internal, custom only) → ISSUED → ACCEPTED \| EXPIRED \| WITHDRAWN \| SUPERSEDED | ACCEPTED, EXPIRED, WITHDRAWN, SUPERSEDED | System (issue/expire), Customer (accept), Admin (withdraw/supersede) | Unique constraint: one Order per Quotation — ACCEPTED cannot fire twice |
| **Custom Sourcing Request** | SUBMITTED → UNDER_REVIEW → SOURCING → QUOTED → (resolved via linked Quotation) \| CLOSED_NO_QUOTE \| CANCELLED | CLOSED_NO_QUOTE, CANCELLED, or implicitly resolved once the linked Quotation is ACCEPTED | Customer (submit/cancel), Admin (review/source/quote/close) | — |
| **Order** (fulfilment track) | PENDING_PAYMENT → CONFIRMED → FULFILLING → COMPLETED \| CANCELLED (only from PENDING_PAYMENT or pre-fulfilment) | COMPLETED, CANCELLED | System (payment webhook → CONFIRMED; all Fulfilments COMPLETED → COMPLETED) | `Order.paymentStatus` is tracked on a **separate** field (UNPAID/PAID/PARTIALLY_REFUNDED/REFUNDED) to avoid a combinatorial status explosion — a COMPLETED order can still carry a REFUNDED paymentStatus |
| **Payment** | INITIATED → PENDING → SUCCEEDED \| FAILED | SUCCEEDED, FAILED | System (initiate), Provider webhook (confirm/fail) | Provider event id unique constraint |
| **Refund** | REQUESTED → PROCESSING → COMPLETED \| FAILED (retry = new record) | COMPLETED, FAILED | Admin (request), Provider webhook (confirm) | New Refund record per attempt, never reused |
| **Fulfilment** | PENDING → PREPARING → READY → DISPATCHED → DELIVERED → COMPLETED; ⇄ EXCEPTION; → CANCELLED | COMPLETED, CANCELLED | Vendor (start preparing, mark ready); READY → DISPATCHED is **origin-dependent** — domestic: Admin only, on collection confirmation; international: **Vendor**, by recording outbound shipment details (per M4, refining the earlier "vendor may dispatch" note — a vendor may never single-handedly move a *domestic* Fulfilment past READY). DELIVERED is System/Admin only, set when the linked Shipment reaches DELIVERED. EXCEPTION is Vendor (report issue) or Admin (delivery failure); resolution (Admin) resumes to PREPARING. ACCEPTED is modeled but unused in M4 (Vendor goes PENDING→PREPARING directly). | Creation is idempotent per Order-confirmation event, not per vendor — since multiple Fulfilments per vendor per Order are legal, vendor-scoped uniqueness cannot be the dedup key. Uses the `Order.fulfilmentsCreatedAt` flag. |
| **Shipment** *(implemented M4)* | CREATED → COLLECTED → IN_TRANSIT → OUT_FOR_DELIVERY → DELIVERED; ⇄ EXCEPTION; OUT_FOR_DELIVERY/IN_TRANSIT → DELIVERY_FAILED → (resume) OUT_FOR_DELIVERY | DELIVERED | Admin/operations only for every status transition — CREATED→COLLECTED is the one moment that means either "domestic pickup confirmed" or "international receipt confirmed" (both land on the same status; disambiguated by `Fulfilment.origin` for display). A customer's `customerConfirmedReceiptAt` is a side signal recorded independently and never itself sets `status = DELIVERED`. | One active Shipment per Fulfilment in the V1 UI (schema allows more later — see entities.md). Confirming collection/receipt requires `status = CREATED`, preventing a double-confirm. |
| **FulfilmentIssue** *(added M4)* | OPEN → RESOLVED | RESOLVED | Vendor (report — only while the parent Fulfilment is PENDING/PREPARING/READY), Admin (resolve, which also resumes the parent Fulfilment to PREPARING) | — |
| **FulfilmentItem payout eligibility** | NOT_ELIGIBLE → ELIGIBLE → ON_HOLD ⇄ ELIGIBLE → CLAIMED | CLAIMED | System (Fulfilment reaches COMPLETED), Admin (hold/release), PayoutRun (claim) | Unique constraint: one claim per FulfilmentItem, ever |
| **PayoutRun** | DRAFT → PROCESSING → PAID \| FAILED (retry = new run) | PAID, FAILED | System (scheduled batch), Admin (manual trigger/mark paid) | New PayoutRun per attempt |

## Notes

- **FulfilmentItem has no independent full state machine** in V1 — its parent Fulfilment carries the primary status, avoiding overbuilt granularity where it isn't needed yet.
- The **payout eligibility trigger** (COMPLETED vs. DELIVERED) is an open business-policy item — see the "must resolve" list in the architecture decision history; the mechanism above works correctly regardless of which trigger is chosen.
- **Refund/payout interaction** across these state machines is detailed in `/docs/workflows/workflows.md` (Workflow K) and ADR 0005.
